## 0. 왜 이 고도화가 필요한가

지금까지의 제품은 **"AI 팀이 한 달에 얼마 드는가"** 에 답한다. 비용 축은 강하다. 그런데 이것만으로는 *계산기*에 가깝고, **AI Native Company(AI를 제품/운영의 핵심 인력처럼 쓰는 회사)처럼 보이지 않는다.**

진짜 AI Native Company는 비용만 보지 않는다. 사람 회사가 인건비뿐 아니라 **성과(무슨 일을 해냈나)** 와 **책임 구조(누가 무엇을 결정·책임지나)** 를 함께 보듯이, AI 팀도 세 가지를 같이 봐야 한다.

```
비용 (얼마 들었나)        ← 이미 있음
업무 성과 (무엇을 해냈나)  ← 축 1 (신규)
책임 구조 (누가 결정·책임) ← 축 2 (신규)
```

이 문서는 이 빈 두 축을 채우고, 외부 발표용 명칭을 다듬는다(축 3). 기존 deterministic(같은 입력이면 같은 결과가 나오는 결정론적 계산)/AI 원칙과 단일 계산 경로 헌법은 그대로 지킨다.

## 축 1 — 업무 산출물 단위 (Work Output / Deliverable, 실제로 만들어낸 결과물)

### 1.1 문제

현재는 Agent가 **호출을 몇 번 했는지(calls)** 만 보인다. 그러나 "API를 30번 호출했다"는 회사 운영 언어가 아니다. 회사는 **"무엇을 만들어냈는가"** 로 말한다.

> 호출 횟수가 아니라 **업무 산출물**이 보여야 AI가 회사 업무를 처리한 것처럼 보인다.

예시 (이게 보여야 함):
- "마케팅 리서치 리포트 1건 생성"
- "고객 문의 12건 분류"
- "세일즈 이메일 초안 30개 생성"
- "계약서 리스크 3건 탐지"
- "대표 승인 필요 항목 5건 생성"

### 1.2 Deliverable을 1급 객체로

호출(call)과 산출물(deliverable, 공유 가능한 결과물 파일이나 업무 결과)을 분리한다. 여러 호출이 모여 하나의 산출물을 만든다 (agent loop, 재시도 포함).

```jsonc
Deliverable {
  id,
  agent_role: "Sales Agent",
  type: "세일즈 이메일 초안",      // 산출물 종류
  count: 30,                       // 만든 개수
  period: "2026-05",
  status: 'produced'               // 생성됨
        | 'passed_review'          // 사람 검토 통과
        | 'reworked'               // 재작업됨
        | 'escalated'              // 사람에게 에스컬레이션
        | 'rejected',              // 반려
  calls_consumed,                  // 이 산출물에 든 호출 수
  cost_attributed,                 // 귀속 원가 (기존 비용 엔진에서)
  operating_decision_ref           // 관련 운영 결정(축 2) 링크
}
```

핵심: **호출·토큰·비용은 산출물에 귀속**된다. 그래서 "이메일 초안 30개 = 호출 90회 = $4.2 = 초안 1개당 $0.14"처럼 *업무 단위 원가*가 자연스럽게 나온다. 이건 기존 `unitEconomics`의 `costPerMetric`(metric당 원가)을 **산출물 종류**로 일반화하는 것이다.

### 1.3 성과 지표 (deterministic 계산, 결정론적 계산)

산출물 데이터에서 결정론적으로 계산한다 (AI 미사용):

| 지표 | 정의 | 의미 |
| --- | --- | --- |
| 처리량(throughput) | 기간당 산출물 수 | "이번 달 리포트 4건, 문의 360건 처리" |
| 산출물당 원가 | cost_attributed / count | "이메일 초안 1개당 $0.14" |
| 검토 통과율 | passed_review / produced | 품질 신뢰도 |
| 재작업률(rework) | reworked / produced | 낭비·품질 문제 신호 |
| 에스컬레이션율 | escalated / produced | 사람 개입 빈도 |
| 자동 처리 비율 | (produced − escalated) / produced | 자동화 성숙도 |

AI(해석)가 하는 일: "CS Agent의 재작업률이 22%로 높습니다. 의료 문의에서 집중 발생 — 프로세스 문제로 보입니다(축 2의 실패 귀인으로 연결)."

### 1.4 설계 시점(Wedge A)과 운영 후(Wedge B) 모두에 적용

- 설계 시점: "마케팅 리서치 리포트 4건/월 예상 → 리포트 1건당 예상 원가 $X"
- 운영 후: 실제 산출물 수·통과율·산출물당 실원가 → **Plan vs Actual** 보정
- 산출물 축이 두 Wedge를 잇는 **공통 언어**가 된다. 비용도, 성과도 "산출물"이라는 같은 단위로 말한다.

### 1.5 화면 영향

- 화면 3(비용·병목)을 **"비용 & 성과"** 로 확장: 비용 옆에 "무엇을 해냈는가" 산출물 보드 추가.
- 산출물 보드 = AI 팀의 *주간 업무 결과 요약*. "이번 주 AI 팀이 처리한 일" 한눈에.

## 축 2 — Human Operating Decision(사람의 운영 결정: 운영자·관리자·책임자 역할)

### 2.1 문제

현재 **Human Approval Gate(사람 승인 관문)**는 좋지만 좁다. 사람이 "OK / Reject"만 하는 자리로 보인다. AI Native Company에서 사람은 단순 승인자가 아니라 **운영자·관리자·책임자**다.

> **Human Approval Gate → Human Operating Decision** 으로 넓힌다.

### 2.2 운영 결정의 6가지 종류

사람이 내리는 결정은 실행 승인만이 아니다.

| # | 결정 종류 | 질문 | 예 |
| --- | --- | --- | --- |
| 1 | 실행 승인 (Approve) | 이 산출물을 내보내도 되는가? | "이 콜드메일 30개 발송 승인" *(기존 게이트)* |
| 2 | 자동화 결정 (Automate) | 이 업무를 사람 검토 없이 자동화해도 되는가? | "문의 분류는 이제 자동화, 검토 면제" |
| 3 | 권한 결정 (Authority) | 이 Agent의 권한 범위를 넓혀도 되는가? | "CS Agent에 50달러 이하 환불 권한 부여" |
| 4 | 기준 변경 (Policy) | 판단 기준·프롬프트·임계값을 바꿔야 하는가? | "리스크 탐지 임계값을 낮춰 민감도↑" |
| 5 | 실패 귀인 (Attribution) | 이 실패는 Agent 문제인가, 프로세스/입력 문제인가? | "재작업 급증은 입력 문서 누락 탓 = 프로세스 문제" |
| 6 | 책임 배정 (Ownership) | 이 Agent의 책임자(사람)는 누구인가? | "Finance Review Agent 책임자 = 대표" |

1번만 OK/Reject고, 2~6은 *운영 결정*이다. 이게 사람을 운영자로 만든다.

### 2.3 책임 구조 (Accountability, 누가 책임지는지)

각 Agent에 **책임자(human owner)** 와 **권한 레벨**, **에스컬레이션 경로**를 둔다. 사람 회사의 조직도와 같은 인터페이스.

```jsonc
AgentAccountability {
  agent_role: "Finance/Legal Review Agent",
  owner: "대표(태나)",                 // 책임지는 사람
  authority_level: 'suggest'            // 제안만 (사람이 실행)
                 | 'act_with_review'    // 실행하되 사람 검토
                 | 'act_autonomously',  // 자율 실행 (저위험만)
  escalation_to: "대표",
  high_risk_tasks: ["계약서 승인"]       // 절대 자율 실행 금지
}
```

권한 레벨은 산출물 성과(축 1)와 연동된다. 예: "CS Agent 자동 처리 비율 96%, 재작업 3% → authority를 act_with_review에서 act_autonomously로 올려도 됨" (단, 운영 결정 #3로 사람이 승인).

### 2.4 운영 결정 → 기록

모든 운영 결정은 **운영 결정 기록(축 3)** 에 남는다. 결정 종류 + 이유 + 가정 스냅샷 + 그때의 성과·비용 근거.

예:
```
결정 종류: 자동화 결정(#2)
무엇: "고객 문의 분류를 자동화, 사람 검토 면제"
이유: "검토 통과율 98%, 재작업 2%, 6주 누적 안정"
가정: "의료/법률 키워드는 여전히 에스컬레이션 유지"
근거 스냅샷: 산출물 360건/통과 353건, 분류 1건당 $0.03
```

### 2.5 화면 영향

- 화면 4(최적화)의 승인 게이트를 **운영 결정 패널**로 확장: OK/Reject + 자동화/권한/기준/귀인 결정.
- (선택) AI 팀 **조직·책임 보드**: Agent별 책임자·권한 레벨·성과를 한 화면에. MVP에선 화면 2(팀 구성)에 책임자·권한 필드를 추가하는 정도로 시작.

## 축 3 — 명칭 변경 (외부 발표용)

내부적으로 Wedge A/B는 괜찮지만, 외부 발표에서 "Wedge A Decision Log", "Wedge B Actual Usage Logs"는 바로 이해되지 않는다. 제품처럼 보이도록 바꾼다.

| 기존 (내부) | 변경 (외부/제품) | 한국어 |
| --- | --- | --- |
| Wedge A Decision Log | **Decision & Approval Log** | 운영 결정 기록 |
| Wedge B Actual Usage Logs | **Actual Usage & Performance Logs** | 실제 사용량·성과 로그 |

추가 권장(같은 맥락):
- "Wedge A / Wedge B"는 내부 설계 용어로만. 외부엔 **"설계(Plan)"**, **"실측(Actual)"** 또는 **"운영 전 / 운영 중"** 으로.
- "Human Approval Gate" → **"Human Operating Decision"**(운영 결정).

명칭이 바뀌면 의미도 넓어진다. "Actual Usage Logs"는 사용량만이지만 **"Usage & Performance Logs"** 는 *무엇을 얼마나 해냈는지*까지 담는다 — 축 1과 정확히 맞물린다. "Decision Log"는 기록이지만 **"Decision & Approval Log"** 는 *결정과 승인이 함께* 흐르는 운영 장부가 된다 — 축 2와 맞물린다.

## 통합 데이터 모델 변경 요약

기존 `AITeamConfiguration`(v0.3 §5, v0.4 §8)에 추가:

```jsonc
AITeamConfiguration {
  // ... 기존 (company_profile, agents, usage, attribution) ...

  deliverables: [Deliverable],            // 축 1 (신규)
  agent_accountability: [AgentAccountability], // 축 2 (신규)

  // 명칭 변경 (축 3)
  decision_approval_log: [OperatingDecision],  // 기존 decision_log 확장·개명
  usage_performance_logs: UsagePerformance     // 기존 usage 확장·개명
}

OperatingDecision {                       // 기존 Decision 확장
  id, ts,
  kind: 'approve'|'automate'|'authority'|'policy'|'attribution'|'ownership', // 축 2
  what, why,
  assumptions,                            // 가정 스냅샷 (기존)
  performance_snapshot,                   // 축 1 성과 근거 (신규)
  cost_snapshot
}
```

원칙 유지: **산출물 수·성과 지표·비용은 deterministic 계산**, **운영 결정의 해석·추천·문장은 AI**. 계산은 여전히 기존 단일 경로(`calculateCost` + `unitEconomics`)를 통과한다.

## 구현 영향 (코드베이스 기준)

| 작업 | 종류 | 비고 |
| --- | --- | --- |
| `Deliverable` 타입 + 산출물 귀속 집계 | 🆕 순수 TS | calls/cost를 산출물에 roll-up(합산). TDD(Test-Driven Development, 실패 테스트를 먼저 쓰고 구현하는 방식) |
| 성과 지표 함수(throughput/통과율/재작업/에스컬레이션) | 🆕 순수 TS | deterministic(결정론적 계산), 100% 커버리지 |
| `unitEconomics` 산출물 단위로 일반화 | ⚠️ 확장 | costPerMetric → costPerDeliverable |
| `AgentAccountability` 타입 + 화면 2 필드 | 🆕 | 책임자·권한 레벨 |
| Operating Decision 패널(6종) | ⚠️ 확장 | 기존 승인 게이트 확장 |
| `decision_log → decision_approval_log` 개명 | ⚠️ 리네이밍 | 스키마에 kind 추가 |
| 산출물 보드 UI(화면 3) | 🆕 | Recharts 재사용 |

신규는 대부분 **순수 함수 + 데이터 모델**이라 기존 TDD·단일 경로 원칙에 그대로 얹힌다. AI 레이어(v0.4 LangGraph)는 해석 프롬프트에 "성과·실패 귀인" 관점만 추가.

## 데모에 미치는 효과

기존 9단계 데모(비용 중심)에 성과·책임이 더해지면 훨씬 "회사"처럼 보인다:

```
[비용]    "이번 달 AI 팀 운영비 28만 원"
[성과]    "리서치 리포트 4건, 문의 360건 분류, 이메일 초안 120개, 리스크 3건 탐지"
[책임]    "자동 처리 94%, 대표 승인 필요 항목 5건"
[결정]    "CS 문의 분류 자동화 승인 (통과율 98% 근거)"
          "Finance Review Agent는 자율 실행 금지 — 대표 책임 유지"
```

> "AI가 답변합니다"(X) → "AI 팀이 이번 달 이런 일을 해냈고, 비용은 이만큼 들었고, 사람은 이런 운영 결정을 내렸습니다"(O). 이게 AI Native Company의 운영 보고서다.

## 한 줄 요약

> AI Native Company는 인건비만 보지 않는다 — **무엇을 해냈고(성과), 누가 결정·책임지는가(책임 구조)** 를 비용과 함께 본다. 그래서 (1) Agent를 호출 횟수가 아니라 **업무 산출물**로 보이게 하고, (2) Human Approval Gate를 **Human Operating Decision**(자동화·권한·기준·실패 귀인·책임)으로 넓히고, (3) 로그 명칭을 **Decision & Approval Log / Actual Usage & Performance Logs**로 바꿔 제품처럼 보이게 한다. 숫자(비용·성과)는 deterministic, 해석·결정 서술은 AI — 원칙은 그대로.
