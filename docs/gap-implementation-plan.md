# 갭 구현 계획 — 결정론 vs 에이전트

> 코드 실측 기반. 마감 6/28 · 혼자 파트타임 전제 → 각 갭마다 "6/28 슬라이스(개념 시연)" vs "이후 프로덕션" 분리.

---

## 0. 핵심 설계 원칙 (지금 아키텍처에서 도출)

지금은 **"통제된 에이전트"** — 진짜 LangChain 1.0 `create_agent` 루프인데 ① 도구 메뉴 스테이지 제한 ② 도구 읽기전용 ③ 숫자 결정론 가드로 묶여 있다. 갭도 같은 원칙으로 나눈다:

- **판단·해석·분류·드래프트 → 에이전트 루프** (모델이 도구 호출, 단 메뉴·권한으로 통제)
- **숫자·계산·실행 → 결정론 + 승인 게이트** (모델에 절대 안 맡김 = 환각·무단실행 0 = 해자)
- **첫 write-tool(메일·빌링)부터는 HITL 승인 + 멱등성 + 롤백 + 원장 기록** (기존 패턴 확장)

---

## 1. 갭별 구현

### A. 공식 계정과목 (chart-of-accounts) — 기준②
- **결정론**: 계정 분류 스키마(무엇이 COGS/인프라/R&D, "요청·호출·토큰"의 정의). 새 파일 `src/domain/accounts/chartOfAccounts.ts`.
- **에이전트**: 지저분한 입력 컬럼을 계정에 *매핑*하는 분류기(LLM 도구, 읽기전용, 사람 확인).
- **에이전트 루프**: Model=분류기 / Tools=계정목록 조회 / SystemPrompt="근거 없는 추측 금지, 모르면 unknown" / State=매핑 후보.
- **수용기준**: 모든 비용이 정확히 1개 계정에 귀속, `unattributed = 0`.
- **6/28 슬라이스**: 스키마 파일 + 데모 매핑 1개. **(싸다)**
- **이후**: 고객별 매핑 학습·예외 처리.

### B. 청구서 대사 (reconciliation) — 보증③ ★해자
- **결정론**: 매칭 수학 — 내 계산 vs 공급사 인보이스 라인 비교, 라인별·합계 Δ. 새 파일 `src/domain/assurance/reconcile.ts`.
- **에이전트**: 차이 *원인 해석·후보 제시*(누락·환율·캐시 미반영 등). 숫자는 결정론, 모델은 설명만.
- **새 도구(읽기)**: 인보이스 파서(공급사 CSV/PDF).
- **수용기준**: 라인별 Δ + 합계 Δ 표시, 허용오차 내 자동 PASS / 초과 시 FLAG.
- **6/28 슬라이스**: *가상 인보이스 vs 계산* 목업 대사 화면(개념 시연). **(중간)**
- **이후**: 실제 공급사 파서·환율·기간 정산.

### C. 예산 대비 실적 (budget-vs-actual) — 예측⑤
- **결정론**: 예산 − 실적 = 변동(절대·%). 새 파일 `src/features/fpna/lib/variance.ts`.
- **에이전트**: 변동 해석·임계 플래그·다음 행동 제안.
- **수용기준**: 변동% 정확, 임계 초과 자동 플래그, 기간 비교.
- **6/28 슬라이스**: 가상 예산 1개 + 변동 표 + 한 줄 해석. **(중간)**
- **이후**: 실적 영속·롤링 예측·시계열.

### D. 골든셋 평가 (quality eval) — 품질 ★여기서 에이전트성 추가
- **결정론**: 골든셋 하네스(입력→기대, 통과율 집계), 프로그램 체크(스키마/인용 — 이미 `interpreter.py`에 일부 있음).
- **에이전트**: LLM-as-judge(루브릭 채점) — 단 사람 라벨로 *보정*, 인용가드 동일 적용.
- **에이전트 루프**: Model=judge / Tools=루브릭·기대값 조회 / SystemPrompt=채점 기준 / State=점수·근거.
- **수용기준**: 같은 입력 재현 가능, judge vs 사람 일치도(kappa) 보고, 골든셋 버전관리.
- **6/28 슬라이스**: 골든셋 10~20개 + judge 스텁 + 통과율 1숫자 + "이렇게 측정한다" 화면. **(중간)**
- **이후**: 보정 운영·드리프트 회귀·use-case별 셋.

### E. 마케팅 · CS 에이전트 — ★진짜 에이전트 + 첫 write-tool
- **Model + SystemPrompt**: `marketing_ops`("브랜드 보이스, 근거 기반, 과장 금지"), `customer_success`("정중·정확, 추측 금지").
- **Tools**: 초안 작성(읽기) + **메일/메시지 발송(쓰기) → HITL 승인 뒤에만**. 첫 write-tool은 반드시 승인게이트 + 멱등성 + 원장.
- **수용기준**: 초안 생성 OK, 발송은 사람 승인 없이는 *차단*(차단 테스트 통과).
- **6/28 슬라이스**: `operatingAssets.ts`에 2 에이전트 역할·권한 등록 + 초안 데모. → "기획/개발/마케팅/CS 4기능 모두 AI팀" 서사 닫힘. **(싸다)**
- **이후**: 실제 발송 연동(Slack/메일)·승인 워크플로우.

## 3. 6/28 현실 컷 (혼자 파트타임)

**들어갈 것(싸고 데모됨)**: A 계정과목 스키마 · E 마케팅/CS 에이전트 등록 · D 골든셋 10개+judge 스텁 · B/C 가상 대사·변동 *목업*.

**미룰 것(펀딩 후)**: 실 인보이스 파서·실 대사 · 영속 예산-실적 · judge 보정 운영 · 실제 메일/빌링 *발송*.

**이유**: 정의적 하드코어의 *프로덕션*은 데이터·시간이 필요. 데모는 "개념 + 설계도", 프로덕션은 로드맵으로 — 그리고 *이 구현 계획 자체가 심사 가점*(뭘 어떻게 지을지 정확히 안다는 증거).
